# Development Roadmap

## Purpose

This document tracks VoxVisit AI development phases and progress separately from technical design documents. Scope, architecture, and fixed project decisions remain defined in the project blueprint.

## Current Status

Phase 0 Design and Decisions is complete. The master blueprint, workflows, state machines, authentication, PostgreSQL database design, agent tool contracts, evaluation strategy, and 20 initial scenarios are approved. Phase 1 Backend Foundation is complete. The FastAPI foundation is implemented and verified against local Docker PostgreSQL 17. The approved PostgreSQL schema is implemented as SQLAlchemy models and three reviewed Alembic migrations: `0001` (24 tables, `btree_gist`, no triggers), `0002` (database hardening), and `0003` (a login rate-limit index). A reproducible, idempotent synthetic data seeder (`python -m app.seed`) loads fictional demonstration data. Patient and staff authentication, PostgreSQL-backed sessions, account lockout, network rate limiting, authorization dependencies, and CSRF and origin protection are implemented and verified locally, with login, logout, and current-session endpoints. PostgreSQL integration tests verify the migrations, constraints, seeder, authentication, and scheduling reads on disposable databases. Read-only scheduling APIs are implemented and verified locally: public clinic directory search, public appointment availability search with a 31-day window, and a verified patient's own appointment list, all with 20-item pages, clinic-timezone-aware times, and an 8-second read timeout. Appointment booking, rescheduling, and cancellation are implemented and verified locally as separate prepare and confirm operations, with atomic READ COMMITTED transactions in the canonical lock order, patient-scoped idempotency, immutable history, and transactional `SLOT_RELEASED` outbox events, covered by PostgreSQL race and rollback tests. A GitHub Actions workflow (PostgreSQL 17 service, locked dependencies, Ruff, `uv lock --check`, migration and schema-drift checks, and the complete database-enabled suite) passed its first real run on GitHub: run 41270577286 on commit `653db6b` (2026-11-01) succeeded on every step, with 800 tests passed and none skipped on PostgreSQL 17.11 and Python 3.11. A reliability review of the appointment transactions corrected the write and read timeouts to bound the whole transaction, repeated the account checks after the locks, and made session refresh tolerate clock skew. A synthetic FHIR-like adapter (Patient, Practitioner, Schedule, Slot, and Appointment resources, read-only, behind the existing authorization, with PostgreSQL as the only store) is implemented and verified locally; it is deliberately not HL7 FHIR conformant and contacts no external system. Waitlist workflows, the `SLOT_RELEASED` consumer, retention jobs, and write-endpoint rate limiting have not begun; outstanding release requirements are listed in `docs/release-controls.md`. Production deployment security controls, listed in `docs/release-controls.md`, still await verification, including appointment-history immutability through restricted database-role grants. Phase 1 scope is complete; what remains is deployment hardening and later-phase work, plus the open decisions recorded in `docs/release-controls.md`. Phase 2 has started: the agent tool layer (the first step) is implemented and verified locally, with a strict four-tool allowlist, the approved response envelope, runtime-owned idempotency keys, sanitized tracing, and no path to confirmation or the commit service. A deterministic evaluation foundation is also in place (the second Phase 2 step): a model-independent runner and a scripted stub model execute EV-001, EV-002, EV-006, EV-008, and EV-016 through that tool layer against a disposable PostgreSQL database, with confirmation performed by a separate trusted UI driver and the zero-count safety invariants enforced by the runner, and with a sanitized machine-readable report of task success, tool errors, retries, bypass attempts, and per-tool latency. The harness was then tightened ahead of connecting a model: scripted decisions are grounded in the patient's words and earlier tool results, a prepared action is checked against the patient's intent before any simulated confirmation, success claims in response text are judged by an independent classifier instead of the model's labels, model failures and malformed decisions are structured failures, and results are independent of scenario order. Baseline measurements only; no thresholds are approved. A first local real-model pilot (the third Phase 2 step) connects one text-based model served by Ollama on the loopback interface to the same tools and harness for EV-001 and EV-016, with bounded calls, timeouts, and malformed-reply handling; its measured results, including EV-001's failure to prepare a booking without asking again, are recorded in `docs/evaluation-strategy.md`. No voice or frontend is connected, and no endpoint exposes the model.

**Phase 2 update.** Phase 2 is **Complete for local development** of the text agent; Phase 3 (local voice) is Not Started. The agent is Approach B: local `qwen2.5:7b` through Ollama reads each message into a structured intent, and a deterministic scheduling controller does everything else, using only the four allowlisted tools; the model cannot confirm anything. Delivered: the agent tool layer and its strict allowlist; multi-turn conversation state per verified session, with recovery when the model's reading fails and credentials never read or requested in chat; backend retirement of outdated pending actions, so a review screen the patient has moved on from can no longer be confirmed; spoken date and time normalization on the clinic's own calendar; and the evaluation harness, with security and concurrency regression tests. The historical frozen A/B comparison was run once and its mechanical decision rule output remains `NEITHER_SELECTED`: it is not a benchmark pass. Approach B was selected by the human reviewer for continued development (21 of 24 correct outcomes against 13 of 24 for the free-form Approach A on that benchmark, under an earlier prompt version) and then passed a separate, frozen 25-conversation acceptance evaluation with 25 of 25 conversations successful and no safety violation (`docs/phase2-acceptance-evaluation.md`). The latest complete PostgreSQL-enabled suite passed 2,021 tests with none skipped. Details are in `docs/text-agent-conversation-layer.md`. Unresolved historical evaluation items are recorded as limitations in `docs/agent-architecture-benchmark-execution.md`, notably that the blinded human audit of the benchmark's reply verdicts was not carried out. Conditions that Phase 3 must handle (speech-recognition errors, latency of the whole voice turn, conversation state across workers, shorter spoken wording) are listed in the acceptance evaluation. Phase 3 and later phases are unchanged.

## Phase 4 Planned MCP Integration Milestone

**Status: PLANNED. Not started and not implemented.** The Model Context Protocol (MCP) integration is an optional feature planned alongside the Phase 4 RAG work. It does not change Phase 4's status, estimate, or RAG exit criterion, and it does not alter the scope of Phase 2 or Phase 3. The planned architecture is recorded in the *Planned MCP Extension* section of the Blueprint v3 planning document, which is currently held back from this repository.

Planned scope:

- A lightweight Python MCP server that gives permitted external MCP-compatible clients a standard interface to VoxVisit AI.
- Initial exposure of two read-only, non-patient-specific tools only: clinic directory search and appointment availability search.
- Reuse of the existing backend services behind the current agent tools. The MCP server adds no scheduling logic of its own and has no separate path to the database.
- Verification before the milestone is complete: MCP tool discovery lists exactly the approved tools, schema validation rejects unknown or malformed arguments, access-control tests show that no patient-specific, preparation, or confirmation capability is reachable, and a security verification of the server and its deployment.
- Patient-specific MCP capabilities are a future step. They are considered only after authenticated client authorization is designed and validated, and they remain subject to the existing patient and session authorization and to explicit UI-only confirmation.
- No MCP tool may confirm or commit an appointment change at any stage.

## Phase 1 Implementation Sequence

1. Establish the FastAPI application, configuration, error handling, and test foundation.
2. Define PostgreSQL schema migrations from the approved database design and run them against local Docker PostgreSQL.
3. Add deterministic synthetic clinics, doctors, patients, credentials, schedules, slots, and appointment fixtures.
4. Implement patient and staff authentication, sessions, authorization, ownership checks, CSRF boundaries, and audit events.
5. Implement clinic, doctor, and available-slot reads.
6. Implement booking, rescheduling, and cancellation with canonical locks, atomic transactions, idempotency, immutable history, and transactional `SLOT_RELEASED` events.
7. Add unit, PostgreSQL integration, authorization, concurrency, idempotency, and retention tests for the approved Phase 1 scenarios.
8. Add the initial GitHub Actions workflow for deterministic tests.
9. Implement the minimal synthetic FHIR-like adapter toward the end of Phase 1. EV-020 does not block the Phase 1 scheduling exit criterion but must pass before the final public release.

This sequence is approved planning. Step 1 is implemented and verified locally. Step 2 is implemented and verified locally: the initial migration applies to a clean database, downgrades cleanly on a disposable database, and matches the models. Rules that need transactional service enforcement, such as the three-session patient limit and cross-table state parity, are deliberately not database constraints and remain for steps 4 and 6. Migration `0002` hardened that schema after code review. Step 3 is implemented and verified locally: a deterministic seeder with explicit-anchor reproducibility, clinic-local daylight-saving-safe schedules, safe repeat execution, and Argon2id credentials read from local environment configuration. Step 4 is implemented and verified locally: separate patient and staff login, hashed server-side sessions with the approved limits, durable lockout and network rate limiting, reusable authorization dependencies, and CSRF protection, with no frontend and no business APIs. Its production cookie, proxy, and CORS behavior remains an implementation-time verification item. Step 5 is implemented and verified locally: the read-only clinic, doctor, and available-slot reads, plus a verified patient's own appointment list, with no booking, rescheduling, cancellation, or waitlist behavior. Step 6 is implemented and verified locally: booking, rescheduling, and cancellation as a prepare operation (a pending action that reserves nothing) and a separate UI-only confirm operation, with canonical locks, atomic transactions, idempotency, immutable history, and transactional `SLOT_RELEASED` events; doctor leave is now scoped to the clinic where it was recorded, in search and booking alike. Step 7 is complete for the implemented scope: the unit, PostgreSQL integration, authorization, concurrency, idempotency, rollback, and clock-handling tests exist. The retention-cleanup jobs and their tests are deferred, not cancelled, to pre-release hardening (Phase 7) because no cleanup job exists yet; they must be built and pass before any public or shared deployment. This narrows the original step and is tracked in `docs/release-controls.md`. Step 8 is complete: the workflow's steps passed against a disposable PostgreSQL 17 from a clean checkout, each guard (version, skipped tests, leaked databases, schema drift) was shown to fail clearly when forced, and the first real GitHub Actions run (run 41270577286, commit `653db6b`) passed every step with 800 tests and none skipped. Step 9 is complete, verified locally and in that CI run: the read-only synthetic FHIR-like adapter with stable identifiers and references, approved status translations, patient isolation and staff permissions, and no writes, covered by unit and PostgreSQL integration tests. Its deterministic mapping assertions are the EV-020 checks that can run before the agent exists; EV-020 must still pass in full before the final public release. Phase 1 is complete. The waitlist, agent, and later phases have not begun, and the release controls and open decisions that remain are tracked in `docs/release-controls.md`.

- EV-020 synthetic FHIR adapter consistency before the final public release.

## Tracking Rules

- Technical documents use descriptive, professional, lowercase kebab-case filenames.
- Phase and step numbers do not appear in technical document filenames, titles, or metadata.
- Development phases and progress are tracked in this roadmap or in GitHub Issues.
- GitHub Issues may track individual tasks after the repository and issue workflow are established.
- Technical decisions remain in their relevant design documents and are not changed by roadmap status updates.
